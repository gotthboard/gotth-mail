--- abstract

This document defines a profile for binding OpenPGP/MIME signed email to an exact configured sender identity.  DKIM authenticates a domain-level mail-handling path, but it does not identify the human, service, role mailbox, automation, or configured sender identity that authored or approved a message.  This profile requires outbound mail to be OpenPGP/MIME signed and requires the signing key fingerprint to resolve to exactly one active sender identity authorized to assert the message's RFC 5322 From and Sender fields.  Ambiguous, unmapped, revoked, expired, disabled, or mismatched signing identities fail closed.

# Introduction

Email already has several authentication mechanisms.  DKIM {{RFC6376}} can prove that a domain signed selected message content and headers.  SPF and DMARC deployments can further constrain domain-level handling.  These mechanisms are valuable, but they do not answer the question this document cares about:

> Which exact configured sender identity signed this message?

For user-origin proof, a domain signature is not enough.  A message can pass DKIM while still being generated by a shared mailbox, a server-side automation, a delegated actor, a compromised workflow, or a local system component.  The receiver or auditing system may know that `example.com` handled the message, but not whether `alice@example.com`, `billing@example.com`, or an approved system identity actually signed it.

OpenPGP {{RFC9580}} and OpenPGP/MIME {{RFC3156}} already provide the cryptographic machinery for message signatures.  This document does not define a new cryptographic algorithm or a new MIME signature format.  It defines a stricter sender-identity profile for systems that require exact sender proof for outbound email.

# Conformance Roles

This profile uses distinct conformance roles.  A deployment can implement one or more roles.

Conforming Sender:
: A system that produces, relays, generates, or approves outbound mail while claiming exact sender identity binding.

Conforming Verifier:
: A system that verifies OpenPGP/MIME signatures and reports whether exact sender binding can be established from available evidence.

Conforming Archive or Auditor:
: A system that stores verification evidence, audit metadata, and policy context for later review.

A generic public receiver often cannot verify private identity databases, delegation records, employment state, or address custody history.  Such a receiver can verify the OpenPGP/MIME signature, signing fingerprint, visible header alignment, and any signed sender-binding assertion present in the message.  Enterprise or local verifiers can additionally verify local identity and policy state.

# Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 {{RFC2119}} {{RFC8174}} when, and only when, they appear in all capitals.

Sender Identity:
: A configured user, service, role mailbox, or system identity that is permitted by local policy to assert one or more RFC 5322 {{RFC5322}} From or Sender addresses.

Signing Key:
: An OpenPGP key or certificate capable of producing an OpenPGP/MIME signature.

Exact Sender Binding:
: A verified relationship in which the signing key fingerprint resolves to exactly one active Sender Identity and that Sender Identity is authorized to assert the message's From and Sender fields.

Authorized Delegation:
: A configured relationship in which one Sender Identity, service identity, or role identity is explicitly permitted by local policy to sign or approve mail asserting another permitted RFC 5322 From or Sender address.

Identity Class:
: The local class of a Sender Identity, such as human user, service, role mailbox, automation, delegated assistant, contractor, guest, or service-only identity.

Delegation Record:
: A versioned local authorization record that permits one Sender Identity, service identity, role identity, or Signing Key to send on behalf of another Sender Identity for a defined scope and lifetime.

Experimental Sender-Binding Assertion:
: An optional signed metadata object that records the sender identity, signing fingerprint, authoritative message identity fields, delegation record if used, timestamp, and policy version for a message.

Fail Closed:
: Refusing to send, accept as valid, approve, or mark as verified when the required signing or identity-binding checks cannot be completed successfully.

# Scope

This profile applies to outbound email produced, relayed, generated, or approved by a Conforming Sender when that system claims exact sender identity binding.

This profile is suitable for administrative systems, webmail systems, notification systems, approval workflows, audit-sensitive mail systems, and systems that need evidence stronger than domain-level DKIM.

This profile does not replace DKIM.  DKIM remains useful domain-level authentication.  It also does not replace S/MIME {{RFC8551}}, although a future document could define a similar exact-identity profile for S/MIME.  This document profiles OpenPGP/MIME.

# Relationship to DKIM

A conforming system MUST NOT treat DKIM as exact sender identity proof.  DKIM authenticates a domain-level signing agent and selected message fields.  It does not, by itself, prove which configured sender identity authorized or authored a message.

A conforming system MAY require DKIM in addition to OpenPGP/MIME signatures.  If both are used, DKIM and OpenPGP serve different purposes:

* DKIM proves domain/server handling.
* OpenPGP/MIME exact sender binding proves the configured sender identity.

# Outbound Signing Requirement

A conforming sender system claiming this profile:

* MUST OpenPGP/MIME sign every outbound email message;
* MUST NOT silently fall back to unsigned email;
* MUST fail closed when signing cannot be completed;
* MUST bind the signature to the canonical MIME entity according to OpenPGP/MIME {{RFC3156}};
* MUST record the signing key fingerprint and identity-binding result in local audit or delivery metadata;
* SHOULD make signature failures visible in operator diagnostics.

Systems MAY exempt imported historical mail from this requirement, but newly sent, resent, forwarded-as-new, automated, notification, approval, or system-generated outbound email MUST be signed before delivery.

# Public Key Discovery

This document is not a key discovery protocol.  It profiles exact sender identity binding after key material or certificate metadata has been discovered by another mechanism.

Recipients and auditors need the sender's public OpenPGP key or certificate to verify a signature.  A conforming sender system claiming this profile MUST provide a public-key discovery mechanism for every Sender Identity that can send outbound mail.

A Conforming Sender MUST support at least one of the following discovery mechanisms:

* a domain-controlled HTTPS OpenPGP Web Key Directory (WKD)-style service for mailbox-address lookup;
* DNS OPENPGPKEY records using RFC 7929 where the deployment chooses DNSSEC/DANE-style publication;
* an authenticated enterprise directory or contact directory;
* explicit manual key distribution with recorded fingerprint confirmation.

A conforming sender system SHOULD support HTTPS Web Key Directory publication because it is widely deployable with normal domain control.  A conforming sender system MAY additionally publish DNS OPENPGPKEY records.  Keyserver lookup alone is NOT RECOMMENDED as the only discovery mechanism because keyservers do not, by themselves, prove that a key is authorized for the asserted Sender Identity.

Discovery is not trust.  A verifier MUST still check the exact sender binding described in this document.  Finding a key for an address does not by itself prove that the key is currently active, unrevoked, unexpired, unambiguous, or authorized for the message's From or Sender fields.

The discovered key material or certificate metadata SHOULD expose enough information for the verifier to display or audit:

* fingerprint;
* user ID or address binding;
* creation time;
* expiration time, if present;
* revocation state, if known;
* publication source.

# Signer-From Alignment

A conforming system MUST verify that the resolved Sender Identity is authorized to assert the RFC 5322 From field of the message being signed.

If the message contains a Sender field, the conforming system MUST verify that the resolved Sender Identity is authorized to assert the Sender field, or that an Authorized Delegation explicitly permits that relationship.

A conforming system MUST NOT treat membership in a group, access to a shared mailbox, successful web authentication, SMTP authentication, DKIM alignment, or possession of a private signing key as sufficient authorization to assert an arbitrary From or Sender field.

A conforming system MUST fail closed when From, Sender, the signing key fingerprint, and the resolved Sender Identity do not align under active local policy.

# Authorized Delegation

Some deployments need service, assistant, workflow, or role identities to send mail on behalf of another address.  This profile permits delegated sending only when the delegation is explicit and auditable.

An Authorized Delegation MUST record at least:

* the delegating Sender Identity or address;
* the delegated Sender Identity, service identity, or role identity;
* the permitted From and Sender fields;
* the signing key fingerprint or fingerprints permitted for the delegation;
* the permitted message-generation context, such as webmail, notification, approval, or service workflow;
* activation time;
* expiration time or review interval;
* revocation state;
* audit owner or approving authority.

A conforming system MUST fail closed when a delegation is missing, expired, revoked, ambiguous, disabled, or too broad to prove the asserted From or Sender identity.

For example, `billing@example.com` MAY be represented by a service Sender Identity such as `billing-system-01` only when local policy explicitly authorizes that service identity and signing fingerprint to assert `billing@example.com` for the relevant message-generation context.

# Sender Identity Resolution

Before a message is released for outbound delivery, the sending system MUST resolve the signing key fingerprint to a Sender Identity.

The resolution result MUST satisfy all of the following:

1. The fingerprint maps to exactly one configured Sender Identity.
2. The Sender Identity is active.
3. The Signing Key is active and usable.
4. The Signing Key is not revoked under local policy.
5. The Signing Key is not expired under local policy.
6. The Sender Identity is authorized to assert the RFC 5322 From field.
7. If a Sender field is present, the Sender Identity is authorized to assert it or the local policy explicitly records the delegated relationship.
8. The message generation context is authorized for that Sender Identity.

If any condition fails, the system MUST treat the message as unsigned or invalid and MUST fail closed.

# Ambiguity and Shared Keys

A signing key that maps to more than one active Sender Identity is ambiguous for this profile.  A conforming system MUST reject ambiguous bindings unless local policy first creates a distinct configured Sender Identity representing the shared role and authorizes that role to assert the message's From or Sender fields.

A Sender Identity MAY have more than one active signing key only when every active key fingerprint is explicitly bound to that Sender Identity and every key has clear lifecycle state.  The existence of multiple keys for one Sender Identity does not relax the requirement that each verified message resolve to exactly one active Sender Identity.

Unknown keys, revoked keys, expired keys, disabled Sender Identities, unmapped keys, and shared keys without an explicit role Sender Identity MUST fail closed.

For example, a shared support mailbox MUST NOT be represented as many individual users using one indistinguishable key.  If a shared role is intentional, it MUST be modeled as a Sender Identity such as `support@example.com` with its own signing key and audit policy.

# Message Fields Covered by Policy

The OpenPGP/MIME signature signs MIME content according to {{RFC3156}}.  RFC 5322 header handling is therefore a security-sensitive part of this profile.  Local policy MUST define which header fields are authoritative for sender identity and MUST bind those fields to the exact sender decision.

At minimum, this profile requires checks over:

* From;
* Sender, when present;
* Message-ID;
* Date;
* Subject, when local policy treats Subject as relevant to audit or approval evidence;
* Reply-To, when local policy treats Reply-To as identity-bearing;
* any local identity assertion headers used by the sending system.

A conforming system MUST NOT allow a user to sign as one identity while presenting a different unauthorized From or Sender identity.

A conforming system MUST fail closed when a message contains multiple RFC 5322 From identities unless local policy explicitly authorizes that exact multi-origin case and records the identities and authorization rule in audit metadata or an Experimental Sender-Binding Assertion.

# Experimental Sender-Binding Assertion

This section is non-normative for core conformance.  Some deployments can include an experimental signed sender-binding metadata part in outbound mail when interoperable deployment requirements permit it.  The metadata part gives verifiers and auditors concrete evidence for the exact sender decision instead of relying only on external logs or user-interface state.

When used, the sender-binding metadata part can use the provisional media type `application/openpgp-sender-binding+json` and can be included inside the signed MIME entity.  The JSON object {{RFC8259}} can contain fields such as:

* `binding_version`;
* `policy_version`;
* `message_id`;
* `date`;
* `from`;
* `sender`, when present;
* `reply_to`, when identity-bearing under local policy;
* `subject`, when local policy exposes the Subject in the metadata object;
* `subject_digest`, when local policy binds Subject without exposing Subject in the metadata object;
* `signing_fingerprint`;
* `sender_identity_id`;
* `sender_identity_class`;
* `delegation_id`, when delegated authority is used;
* `delegation_expires`, when delegated authority is used;
* `asserted_at`;
* `result`, using a verification result from this document or a local equivalent.

When `subject_digest` is used, the digest object needs to identify the digest algorithm and digest value.  Digest input canonicalization is local policy unless a future revision of this document defines an interoperable canonicalization profile.  Implementations using this experiment ought to use a collision-resistant digest algorithm and record the canonicalization rule in policy metadata.

An Experimental Sender-Binding Assertion is not a substitute for cryptographic OpenPGP/MIME verification.  The assertion is useful only when it is covered by the valid OpenPGP/MIME signature and the signing fingerprint resolves under the exact sender rules in this document.

A sender that does not include an Experimental Sender-Binding Assertion still has to satisfy the core requirements of this profile, including equivalent audit metadata and exact sender binding before delivery.

This document does not request IANA registration for `application/openpgp-sender-binding+json` in this revision.  The media type is described as an experimental deployment mechanism for review and interoperation testing.

# Key Lifecycle Requirements

A conforming system MUST define key lifecycle behavior for:

* key creation or enrollment;
* fingerprint-to-identity binding;
* rotation;
* revocation;
* expiration;
* disabled users;
* deleted users;
* delegated or role identities;
* recovery after key loss.

A conforming system MUST fail closed when key state cannot be determined.  Convenience delivery is not a valid reason to send unsigned mail under this profile.

# Verification by Receivers and Auditors

A receiver or auditor validating this profile SHOULD verify both layers:

1. The OpenPGP/MIME signature is cryptographically valid.
2. The signing key fingerprint resolves to exactly one active Sender Identity authorized for the message's From and Sender fields.

A receiver that can verify the OpenPGP signature but cannot verify the sender-identity binding SHOULD report the message as cryptographically signed but not exact-sender-bound.

# Verification Result Taxonomy

A conforming implementation SHOULD distinguish at least the following verification results for audit logs, operator status, and test suites:

* `valid_exact_sender`: the OpenPGP/MIME signature is valid and the signing key resolves to exactly one active Sender Identity authorized for the message's From and Sender fields.
* `valid_delegated_sender`: the OpenPGP/MIME signature is valid and the asserted From or Sender field is authorized by an active, scoped, unambiguous Delegation Record.
* `valid_domain_only`: domain-level authentication, such as DKIM, passed but exact sender binding was not established.
* `valid_signature_unbound_sender`: the OpenPGP/MIME signature is cryptographically valid but no exact Sender Identity binding was verified.
* `ambiguous_signer`: the signing key maps to more than one active Sender Identity.
* `mismatched_from`: the resolved Sender Identity is not authorized to assert the From field.
* `mismatched_sender`: the resolved Sender Identity is not authorized to assert the Sender field.
* `revoked_signer`: the signing key or Sender Identity has been revoked under local policy.
* `expired_signer`: the signing key, Sender Identity, or delegation has expired under local policy.
* `disabled_sender_identity`: the Sender Identity is disabled.
* `unsigned`: no required OpenPGP/MIME signature was present.
* `verification_error`: verification could not be completed.

These states are not protocol wire values in this document.  They are diagnostic categories intended to prevent implementations from collapsing materially different states into a vague `signed` or `valid` boolean.

# Audit Metadata

A conforming sender system claiming this profile MUST record enough audit metadata to reconstruct the exact sender-binding decision for each outbound message.

The audit record SHOULD include at least:

* message identifier;
* message generation time;
* RFC 5322 From field;
* RFC 5322 Sender field, when present;
* signing key fingerprint;
* resolved Sender Identity identifier;
* Sender Identity class;
* policy version;
* relevant identity-state or timeline reference;
* delegation identifier or authorization rule, when used;
* verification result from the taxonomy in this document;
* reason for failure when a message is blocked;
* signing component or workflow that produced the message.

Audit metadata MUST NOT be exposed in public message headers unless local policy intentionally permits that disclosure.  Public headers can leak stable internal identifiers and delegation structure.

# Examples

## Individual User Mail

`alice@example.com` sends a message from an account configured as the Sender Identity `alice@example.com`.  The message is OpenPGP/MIME signed with a key fingerprint explicitly bound only to that Sender Identity.  The From field is `alice@example.com`, no conflicting Sender field is present, the key is active, and the identity is active.  The result is `valid_exact_sender`.

## Shared Role Mailbox

A support team sends mail as `support@example.com`.  This profile does not permit one indistinguishable shared key to represent several individual users.  The conforming deployment creates a Sender Identity for `support@example.com`, binds a role signing key to that identity, and records local audit data about the authenticated actor or workflow that caused each message to be sent.  The result can be `valid_exact_sender` for the role identity, not for an unnamed individual human.

## Delegated Service Mail

A billing service sends mail with From `billing@example.com`.  The signing key belongs to service Sender Identity `billing-system-01`.  Local policy explicitly authorizes `billing-system-01` and its fingerprint to assert `billing@example.com` for billing workflow messages.  If the delegation is active and unambiguous, the result can be `valid_delegated_sender`.

## DKIM Pass Without Exact Sender Binding

A message passes DKIM for `example.com`, but it has no OpenPGP/MIME signature or its signing key cannot be mapped to exactly one active Sender Identity authorized for the From field.  The result is not exact sender binding.  Depending on available evidence, the result is `valid_domain_only`, `valid_signature_unbound_sender`, `unsigned`, or another failure result.

## Wrong Sender Field

A message is signed by a key bound to `alice@example.com`, but the From field is `bob@example.com` and no active delegation authorizes Alice's Sender Identity to assert Bob's address.  The system MUST fail closed and report `mismatched_from`.

# Threat Model

This profile is intended to reduce the following threats:

* confusing DKIM domain authentication with exact user, service, or role identity proof;
* compromised application servers sending as arbitrary users without exact signing authorization;
* shared mailbox ambiguity where several actors are hidden behind one indistinguishable key;
* stale, revoked, expired, or disabled employee keys continuing to produce accepted mail;
* automation claiming a human identity without an explicit delegation record;
* fail-open delivery during signing, key lookup, or identity-service outages;
* audit systems storing only `signed=true` without enough information to reconstruct who was authorized to sign.

This profile does not by itself prevent compromise of a valid signing key or endpoint.  It requires implementations to make the identity binding explicit, auditable, revocable, and failure-closed.

# Operational Identity History

Operational identity history, address custody, key custody, search indexing, downgrade timelines, and forensic export are important for deployments that need long-lived auditability.  Those topics are intentionally separated from this core profile.  See `draft-hunn-exact-sender-operational-identity-history-00` for an operational companion profile.

# Resend, Forward, and Mailing List Behavior

Forwarding an old signed message can preserve old evidence, but creating a new outbound message that asserts a current Sender Identity requires a new exact-sender-bound signature under current policy.

A conforming system MUST generate a new signature when message content is modified, when a message is forwarded as a new message, or when a message is resent in a way that asserts a current identity.

Mailing lists and gateways often rewrite headers, rewrap MIME content, or append list material.  Exact sender binding does not survive such mutation unless the list or gateway creates a new exact-sender-bound signature as its own Sender Identity.  A conforming verifier MUST NOT treat a mutated list message as still exact-sender-bound to the original author unless the original signed entity remains intact and the displayed identity is not misleading.

# Security Considerations

This profile is intended to prevent systems from confusing domain-level provenance with exact sender identity.  The primary failure mode is accepting DKIM, SMTP authentication, a web session, or a shared mailbox as if it proved user-origin authorship.  That is not enough.

Implementations need to protect signing keys.  Server-held private keys create a high-value target and need strong storage, access control, auditing, and rotation.  Hardware-backed keys or client-held keys can reduce server compromise impact, but they complicate webmail and automation workflows.

A valid OpenPGP signature does not prove the signer intended every displayed rendering of a complex MIME message.  MIME canonicalization, signed part selection, attachment handling, and HTML rendering are security-sensitive and need explicit testing.

Replay and resend workflows need care.  Re-sending a historical signed message can preserve old evidence, but sending a new outbound message that asserts a current identity requires a current valid signature under current policy.

A system MUST NOT allow unsigned fallback during outages.  Fail-open behavior destroys the profile.

# Privacy Considerations

Exact sender binding may reveal stable key fingerprints and stronger identity linkage than domain-level authentication.  Implementations SHOULD disclose this to users and avoid leaking unnecessary internal identity metadata in public headers.  Audit systems SHOULD retain enough evidence for verification while respecting local retention and privacy rules.
